Dynamic Elemental Services

A contract for delivering runtime-supplied node data — platform, hostname, RKE2 role, join tokens, SSH keys, Helm overrides — without rebuilding the Product Image. Provider Ignition writes files on first boot; Elemental services consume them by explicit path.

00What's known when

The Product Image is built once. But six-plus pieces of deployment data only exist at runtime. Dynamic services bridge that gap without a rebuild.

Baked at build time

Operating system · Kubernetes distribution · product components — fixed inside the Product Image.

Only known at runtime

Infrastructure platform · hostname · RKE2 role · cluster join data · SSH keys · resource-deploy authority · deployment-specific Helm values.

02Boot mechanisms focus

Dynamic Elemental Services rest on two initramfs mechanisms (dracut modules that depend on the Ignition dracut module) and one installed-system mechanism (the generated Elemental service).

initramfs · dracut

29elemental-platform-resolver

Installs elemental-platform-resolver.service + .sh. Runs after udev settles and before the Ignition fetch/disk/file/complete units. Writes PLATFORM_ID into /run/ignition.env ahead of provider fetch.

It also patches Ignition's systemd generator in the target initramfs so an already-resolved PLATFORM_ID survives later generator reruns — generic virtualization detection can't overwrite a Platform-Hint value.

initramfs · dracut

30elemental-ignition-merge

Installs elemental-ignition-merge.service + .sh. Runs after ignition-setup-user.service and before the same Ignition fetch/disk/file/complete units. Stages the Product Image base Ignition before Ignition evaluates system + provider config.

Keeps two roots distinct — see § Merge helper.

installed system

Generated Elemental service — elemental-k8s-dynamic.service

Runs after Ignition has written files, and calls elemental3ctl k8s-dynamic apply --config <path>. This is the first Elemental component that reads Dynamic Node User Data. Dracut never parses that runtime file — it only guarantees the platform and base-Ignition inputs are ready before Ignition runs.

05Merge helper — two roots

The merge helper exists to move one file from a source it understands into a target stock Ignition understands. Keeping these distinct is the whole job.

Source — embedded Ignition media
/ignition/elemental-merge (marker) /ignition/config.ign (flattened base)

May mount /dev/disk/by-label/ignition; handles the nested /ignition/ignition layout.

→
Target — Ignition system config root
/usr/lib/ignition/base.d/10-elemental-base.ign

The SUSE Ignition system config path consumed by stock Ignition on the installed system's first boot.

After the handoff, stock Ignition is solely responsible for loading runtime provider data. elemental3 customize --mode merge produces the embedded partition + marker. Scope is the installed system's first boot — not ISO live-boot merge semantics.

06The ownership boundary

The single rule that keeps the design clean.

Provider Ignition Config is still Ignition data.
Dynamic Node User Data is Elemental data.

Provider Ignition Config may write Dynamic Node User Data to disk — but Elemental never reinterprets provider metadata as Elemental configuration.

Why not parse provider metadata in Elemental?

It would duplicate stock Ignition provider behavior and change failure semantics for invalid Provider Ignition Config.

Failure semantics

recoverable Missing/invalid service input file → diagnostic, node repairable. Invalid Provider Ignition Config itself stays a stock Ignition failure.

07k8s-dynamic — the first service

Enabled via dynamic_service.yaml, generated only for merge-mode images.

dynamic_service.yaml
Provider writes (Ignition)
Node User Data (Elemental)
apply → derived files
services:
  k8s-dynamic:
    enabled: true
    config: /var/lib/elemental/k8s-dynamic/userdata.yaml
    timeout: 120

enabled opts in · config is the explicit path passed to the unit · timeout is the systemd timeout (s). Valid only for merge-mode images.

// normal Ignition storage config — provider's job
{
  "ignition": { "version": "3.5.0" },
  "storage": { "files": [{
    "path": "/var/lib/elemental/k8s-dynamic/userdata.yaml",
    "mode": 420, "overwrite": true,
    "contents": { "source": "data:,hostname%3A%20node1..." }
  }] }
}

The provider writes the file. Dracut does not parse it.

hostname: node1.example.com
rke2:
  type: server      # server | agent
  init: true        # writes init.yaml
  token: my-cluster-token
elemental:
  kubernetes:
    deployResources: true  # default true; set explicitly for multi-node
helm:
  values:
    rancher: { hostname: rancher.example.com }
users:
  - name: root
    ssh_authorized_keys: [ ssh-ed25519 AAAA...root@example ]
$ elemental3ctl k8s-dynamic apply --config <path>

# validates first, then on success:
  ✓ write /etc/hostname
  ✓ write SSH authorized keys
  ✓ render RKE2 init.yaml | server.yaml | agent.yaml
  ✓ create resource-deploy marker  (if deployResources)
  ✓ apply Helm overrides           (only to image-enabled charts)

# on failure → recorded in:
  /var/lib/elemental/k8s-dynamic/status.yaml
  # fix the file, rerun apply.
Helm overrides may change values only for charts already enabled by the Product Image. Unknown charts or invalid overrides are recoverable errors in status.yaml.
